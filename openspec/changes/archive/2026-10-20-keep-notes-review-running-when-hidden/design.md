# Design

## Context

动机见 [proposal.md](proposal.md)。`AppState.notesReview` 已在应用级持有 `NotesReview`，无需引入后台服务。当前 `LauncherSession.closeReview()` 同时清空视图状态并调用 `review.cancel()`，面板隐藏也经过此路径。`syncReview()` 已要求回顾展开且周期匹配，隐藏期间通知不会重新打开界面。

## Goals / Non-Goals

- 将展示生命周期与单个生成任务分离，继续使用已有任务身份、最终校验和周期缓存。
- 不增加任务持久化、后台扫描、并行周期任务、新的权限或依赖。

## Decisions

### 展示关闭仅清除展示状态

让 `closeReview()` 仅清理会话镜像状态，不调用生成服务的取消方法。现有 `onChange` 与 `syncReview` 的展开检查隔离隐藏期间的结果。替代方案是给每个关闭调用增加保留参数，但容易遗漏编辑、切模式和详情切换等入口，并产生不同关闭行为。

### 保留单个活动请求

沿用 `NotesReview.load` 的同周期／同配置请求复用，以及不同周期或强制刷新时取消旧请求的机制。重开路径须先刷新权限，再检查活动请求；当前提前返回只检查周期与配置，必须同时检查今天回顾的冻结起点与本地今天零点是否一致。避免跨日重开时继续显示昨天的运行任务。周回顾沿用冻结的最近七天窗口。

后台完成仍按既有完整流和解析规则缓存，隐藏期间失败不自动重试；主动重开可按既有规则重试或复用旧完成缓存。不新增每周期并行任务，以免额外调用模型和改变切周期语义。

### 保留真正失效时的取消

保留配置观察、权限校验、范围版本和请求身份检查；禁止把 `cancel()` 本身改为空操作。关闭回顾展示与关闭回顾功能开关含义不同。模型／权限失效仍撤销任务和缓存，应用退出不提供续跑保证。

## Risks / Trade-offs

- 隐藏后仍占用一次读取／模型请求 → 仅继续用户已启动的有界任务，不自动扫描或重试。
- 同周期重开意外先取消再生成 → 检查打开路径中的预先关闭调用及 `load` 的提前返回条件。
- 旧请求在取消后返回 → 保留请求身份及配置校验，禁止旧结果覆盖新请求或写入缓存。
- 原始长等待原因仍未复现 → 将隐藏取消修正与耗时诊断区分，不用编译成功代替真实行为验证。

## Migration Plan

无数据迁移。实现后同步相关主规格；回退代码及对应规格即可恢复原行为。遵循仓库规则，不自动启动或操作应用窗口。
