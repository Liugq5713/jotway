# Codex action

> Role: **Current**

The Codex action starts a task when the user confirms the draft. It requires no project selection and no second send in Codex. The existing ChatGPT action remains a separate, manual-send prefill route.

## Setup and routing

In Jotway, open Settings → Apps → Codex → Set Up Codex. The Terminal installer first installs the read-only `jotway-codex-check-v1.sh` in `~/Library/Application Scripts/com.liuguangqi.jotway/`, then checks Codex CLI and its existing login before installing `jotway-codex-v2.sh`. If the CLI is missing, the check script remains installed and setup reports that CLI installation is still needed. Install a CLI with app-server support and sign in yourself with `codex login`, then run setup again. The installer never installs Codex, signs you in, or replaces different existing scripts (including symlinks). Upgrading from a v2-only installation requires this explicit setup once to add the check script; the matching v2 helper remains unchanged. v1 execution helpers remain intact and are not used as a fallback. Return to Jotway and use Check Setup if needed.

The check script only locates an executable `codex`; it does not run the CLI, read credentials, create a session or change configuration. It uses the execution helper's PATH: `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, system binary directories, then the inherited PATH. It does not source shell startup files. A CLI installed outside this environment may remain undetected. Jotway does not read, copy, or store Codex credentials.

Codex shows checking, CLI missing, setup needed, ready or check failed. Missing/non-executable scripts need setup; unknown or failed detection does not mean the CLI is missing. Only a successful CLI check plus the execution helper permits tasks; no Codex desktop app is required. Ready does not guarantee login, account access or protocol compatibility. Settings and Open Task Folder stay available in every state.

Startup and panel presentation request a read-only check when the action preference is enabled. Settings appearance, Check Setup and returning from Terminal also request checks. Concurrent checks are merged; each waits at most three seconds and accepts at most 1 KiB of fixed protocol output. A timed-out script's late result is ignored, and no second process starts until it exits. Typing does not launch a probe. Detection never changes `actionEnabled.codex`; automatic recovery respects a user's disabled preference. When disabled, ordinary display refresh does not probe, while the dedicated settings can explicitly check.

Select Run with Codex in the target menu, enter the task and confirm with Enter or Command+Enter. An `@` template query opens writing templates; selecting one only fills editable text and preserves the Codex target. It never starts a task or setup.

While Codex is explicitly selected, the lower card shows the five most recent tasks started from Jotway, newest first, even with an empty editor. Template and target menus temporarily cover it. Rows show the actual conversation name, status and start time; task excerpts or Untitled conversation are fallbacks. Clicking opens the conversation link, then result.md or the task folder if needed. Successful opening clears the editor and selected target; if all destinations fail, the draft remains for retry. Browsing never submits or restores a task. Switching target hides the list. Ordinary confirmed submission still clears and hides the panel.

Task folders retain `.jotway-task.json` with a title excerpt (at most 120 characters), optional conversation name, start time, status, and conversation ID. These records are separate from optional local operation recording. Loading runs off the input path, without reading Codex's private database or full result bodies. After restart, previously running tasks show Check result because their outcome cannot be confirmed. Older task folders with a result or conversation shortcut remain clickable using their folder creation time; saved conversation IDs can also retrieve names. Metadata-storage failure does not change a completed task into a failure or trigger a retry.

When the shared dependency state is ready, opening the list refreshes names through the installed helper using `initialize` and at most five `thread/read` requests with `includeTurns: false`. The list first shows cached names, limits refreshes to once per thread per 30 seconds, and cancels the read connection after five seconds or when its view disappears. Missing dependencies or read errors retain cached names; unavailable states do not launch a name connection. The active execution connection also captures `thread/name/updated` events. Names come from Codex's `thread.name`; Jotway does not generate or rename conversations. A missing or explicitly cleared name falls back to the task excerpt. The read connection never calls `thread/start`, `thread/resume`, or `turn/start`. See the [official stored-thread interface](https://learn.chatgpt.com/docs/app-server#read-a-stored-thread-without-resuming).

Old `@codex` text remains literal and does not select Codex, start setup or remove a prefix. Explicit Codex submits the whole text using its ordinary surrounding-whitespace rule. Empty tasks cannot execute. Codex has no fallback priority.

The target capsule stays available for ordinary old-prefix text. An unavailable explicitly selected Codex target blocks submission instead of routing elsewhere. Templates neither lock the target nor bypass availability checks.

When a check or execution script needs setup, the target menu offers Set Up Codex. Checking, CLI-missing and failed-check states provide neither an executable Codex candidate nor a menu setup shortcut; dedicated settings retain repair and recheck controls. Completing setup retains the draft and selects Codex; press Enter again to start the task. The action defaults to enabled and uses the shared `actionEnabled.codex` preference. Its setup page stays available in Settings.

## Execution

Only a confirmed submission starts task execution through macOS `NSUserUnixTask`. Selecting the Codex target can also start a bounded, read-only helper connection for conversation names; it never starts model work. Ordinary typing and preparation before confirmation do not launch a probe or Codex. After confirmation, preparation waits for a new probe that started after that confirmation; an older in-flight check cannot satisfy it. Reconfirming the same ready state does not invalidate its own preparation. Changes to the draft or target discard the old preparation. The runner rechecks shared readiness and helper files before creating a task, and the unchanged helper checks CLI lookup immediately before launch. Sandboxed Jotway reads the user-installed helper; the system runs it outside Jotway's sandbox so the CLI can use its own existing authentication and configuration.

Each task receives a new UUID directory under Jotway's Application Support `Codex Tasks` folder. This is an output workspace, not a Git repository or saved project. The helper runs:

```sh
codex app-server --listen stdio:// \
  -c 'approval_policy="never"' -c 'sandbox_mode="workspace-write"'
```

Jotway exchanges newline-delimited JSON-RPC over stdin/stdout: `initialize` → `initialized` → `thread/start` → `turn/start`. The client identifies itself as `jotway`. Each new thread is persistent, uses the task directory as its cwd, and explicitly requests `approvalPolicy: never` and `sandbox: workspace-write`. Every new task requests `model: gpt-6-astra` in `thread/start`, then `model: gpt-6-astra` and `effort: high` in `turn/start`. Every confirmed Codex submission uses these fixed values. The CLI supplies its own login and other configuration. The prompt is a JSON text input, never a shell expression or a command argument. Reads consume available pipe bytes immediately so a short initialization response cannot stall while waiting for a full buffer.

These request settings override the CLI defaults only for new Jotway tasks. They do not modify global configuration, migrate existing conversations, or affect the read-only name lookup. Existing v2 helpers do not need reinstalling for these settings to take effect after an application update. If Codex rejects the model or effort, Jotway keeps its existing failure handling: rejection before `turn/start` fails the attempt, while rejection after submission leaves the result uncertain. It never removes the settings, substitutes another model, retries automatically, or marks a rejected request as completed. Account access to the requested model is determined by Codex.

App-server creates interactive-source threads (`vscode` in the supported CLI), which the default `thread/list` source filter includes. Jotway checks the returned source before submitting the task. Desktop visibility can still depend on the active account, project/section filters, and refresh behavior; Jotway does not control that UI. Existing exec threads keep their original source. See the [sidebar research](../development/codex-sidebar-research.md) for upstream behavior and recovery options.

This background client declines permission requests and supplies no interactive answers. Tasks requiring expanded permissions or clarification may be unable to finish. Keep Jotway open during execution. Quitting writes cancellation markers that the helper checks once per second before terminating its Codex child.

Jotway drains JSONL output continuously, correlates events to its thread and turn, and retains the last final agent reply for `result.md`. Only `turn/completed` with status `completed` and a valid thread ID confirms success. Failed or interrupted turns are not successful; creating a thread or starting a turn alone is not completion. Model-reported limitations can still appear in a completed answer, so the user reviews the result. Jotway then closes stdin, drains shutdown output, and lets the helper exit. A later shutdown or result-storage error cannot turn confirmed completion into a retry. Confirmed completion is recorded as `completed`, separately from submission acceptance.

Completion notifications default to off for all actions. Settings → General → Completion Notifications enables them, including the quiet “Codex task finished.” notice at the top-right of the screen containing the pointer. The current preference is checked when completion arrives. Jotway does not automatically open Codex, `result.md`, or the task folder. The notice cannot become a key or main window, does not activate Jotway, and uses no sound or notification-center permission. It closes after four seconds; hovering pauses dismissal and leaving gives another four seconds. A close button dismisses it immediately. Clicking the notice body opens that task's `codex://threads/<threadID>` conversation link. If macOS cannot open the link, Jotway tries its `result.md` instead; failure to open either shows an error without rerunning the task. Accepting a URL does not confirm that the destination application finished navigating. New completions reuse the same notice and restart its timer. Displaying, clicking, or closing the notice cannot execute the task again, alter a draft, or change the recorded result.

Settings → Apps → Codex → Open Task Folder opens the existing `Codex Tasks` directory in Finder, including results from before this navigation support. Each newly completed task also saves `Open in Codex.webloc` beside `result.md`, containing only its conversation URL. This preserves an explicit conversation entry after the notice disappears or Jotway restarts. A shortcut-write failure does not change the completed execution outcome or trigger a retry. If saving the final reply fails, the conversation remains the primary entry and the task directory becomes the notice's fallback destination. Older task folders retain their results but do not receive shortcuts retroactively. Jotway does not inspect Codex's private database or change its history filters.

Dependency failures retain the draft and explicit Codex target without rerouting or automatically retrying. Availability changes do not cancel already accepted tasks or delete their history. Launch failures restore the draft through the shared recovery flow. Failures after submitting `turn/start` are reported as uncertain because the task may already have changed files, even if the start response was lost. There is no automatic retry. Task directories/results and Codex's own conversation history remain on disk; the lower card exposes only the five most recent Jotway tasks. Raw protocol output, prompt text, and external error messages are excluded from Jotway runtime logs.

## Interfaces

- [Codex app-server](https://learn.chatgpt.com/docs/app-server): initialization, persistent threads, turn streaming, and approvals.
- [Apple NSUserUnixTask](https://developer.apple.com/documentation/foundation/nsuserunixtask): the user-script execution boundary.

## Runtime path

Availability, execution and the user-invoked installer use the account home’s existing `Library/Application Scripts/com.liuguangqi.jotway` directory. Leaving the main-app sandbox does not create a new script location, require login again or overwrite a different installed helper. Codex task data follows the app-owned migrated Application Support root. See [Direct distribution runtime](../../openspec/specs/direct-distribution-runtime/spec.md).
