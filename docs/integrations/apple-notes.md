# Apple Notes action

> Role: **Current**

Notes is the only bundled storage fallback. Its shared history index, embedding, scope and pause controls remain independent of model fallback and the save destination.

Apple Notes is the preferred storage fallback once a destination is configured and no known permission failure prevents execution. When it needs configuration, the panel offers Set Up Notes as an explicit target and as the fallback when no other storage action can execute.

## Routing

Explicit phrases such as “记一下”, “存备忘录”, “save to notes”, and “take a note” can match locally, including when Notes needs setup. A user can select Notes directly from the target menu. Routing does not request a model; setup is never an execution candidate or a prewarmed action.

The `@` picker offers input templates and only edits the draft. Old `@notes` text is literal, including when Notes is explicitly selected. Before supplementation and saving, Jotway preserves the complete original draft, its leading text and whitespace; it does not remove an action marker.

Without a stronger explicit target, bundled keyword or qualified local application match, Notes is the only bundled storage fallback. If it is not ready, Set Up Notes opens configuration. An unavailable explicit target retains its error instead of silently switching to Notes.

## Authorization and configuration

Pressing Enter or Command+Enter in the editor with Set Up Notes selected opens a single configuration window with an Allow Access button and an explanation of the default destination. Clicking Allow Access makes the Apple Events request that can trigger the macOS consent dialog. Opening the setup window or action settings page, typing, rendering the panel, background recognition, and action prewarming do not request Notes permission.

After authorization, Jotway keeps the saved destination when it is still available. Otherwise, it selects the default folder in the default Notes account, then another account's default folder, then the first exposed folder if no account default is available. Successful launcher setup completes automatically. Settings → Apps shows the selected destination and offers Change… to open the optional folder picker; the launcher setup window has no picker. Authorization and destination selection do not create a test note, and no verification step is required.

The draft, selection, and draft identity are retained while recognition is paused. Repeated confirmation focuses the existing configuration window. Completing, cancelling, or closing configuration returns to the same draft; successful configuration selects Notes and waits for another Enter before saving. A stale configuration callback cannot replace a newer draft or take its focus. Setup does not clear the draft, play a submission animation, or record action execution or model-adoption feedback.

Permission refusal and revocation retain the selected destination and direct the user to System Settings → Privacy & Security → Automation → Jotway → Notes. When authorization or the saved destination needs repair, settings and launcher setup offer Open System Settings and Allow Access Again. They do not reset permissions or promise that macOS will show the consent dialog again. A successful authorized read clears the known permission-failure state.

## Execution

The following preparation-first flow applies when daily grouping is disabled. The default grouping flow is described below.

1. On confirmation, freeze the complete original draft and action configuration, reject whitespace-only content, and immediately clear the accepted draft and hide the panel.
2. Run optional related-history retrieval and AI supplementation in the background. Model output contains only bounded supplement items and evidence-backed history associations, never replacement note text, tags or a title.
3. Resolve the initial title independently, assemble the title, a blank line, complete original text and any valid additions, persist complete non-content boundary fingerprints, then create one note through the Apple Notes adapter. Closing or reopening the panel does not cancel an accepted submission. A pending title may later receive a guarded title-only update; ordinary supplements are not refreshed.

After Notes confirms the original save with a note identifier and any required readback, Jotway shows a lightweight “Saved to Notes” completion notice without automatically opening the note or taking keyboard focus. Clicking the notice body opens or activates Notes; it does not save another note or promise to select the created note. Submission acceptance and background supplementation alone do not trigger this notice. It follows the shared [completion feedback](../product/overview.md#completion-feedback) behavior.

The ordinary path adds an independent semantic title and a blank line, then includes the complete original body once in each HTML and plain-text representation. It does not remove action markers or the first original line. It preserves leading and trailing whitespace, blank lines, repeated spaces, tabs, indentation, intentional repeated lines, Markdown-looking text, code, URLs, paths, and escaped HTML special characters. Line endings may be normalized and a final newline may be appended. Ordinary notes have no grouped timestamp. Titles and other display metadata are excluded from original extraction through a complete boundary, never by guessing which first line to remove. Other actions retain their existing trimmed-body contract.

AI supplements contain zero to three useful analyses, suggestions or decision conditions. A draft that asks a question can receive a direct, separate response based on the draft and supplied history; ordinary captures receive additions only when useful. Historical proposals do not establish what is still unfinished: missing completion evidence is marked as unknown, and conflicting or later completion records are considered together. For progress questions, relevant historical issues become candidates to verify with concrete completion checks; unknown status alone does not require an empty response. There is no fixed Background / Idea / Question template. No incremental information means no AI section. After final filtering, any accepted additions follow the original and one visible divider (`────────────────────────────`). AI insights appear before related content. Chinese drafts use the bold headings “AI 洞察” and “相关内容”; other drafts use “AI Insights” and “Related Content”, independently of the English app interface. Generated content uses left-aligned system body fonts and colors, without quote or first-line indentation. The original keeps its whitespace-preserving HTML region. No accepted additions means no divider or generated headings.

Each historical association contains a short relationship explanation followed immediately on the next line by `来源：《短标题》↗`, or `Source: Short title ↗` for non-Chinese drafts. The title decoration and arrow form one link to the real source ID; the source prefix is outside the link. Source titles have whitespace normalized, one existing outer pair of Chinese book-title brackets removed before decoration, and a 48-character limit with ellipsis; empty titles use “无标题笔记” or “Untitled note”. HTML special characters remain literal text. Saved output has no separate Sources list, modification dates, excerpts or source-opening instructions. Empty sections are omitted.

Generated layout inserts exactly one blank line after the divider, between each heading and its first item, between adjacent insights or related entries, and between the two sections. An explanation and its source have only a line break. The original retains all of its own trailing blank lines; the writer only supplies any missing separation before the divider. HTML rows and plaintext follow the same order; plaintext uses two line feeds for one blank line and retains the final newline convention. Natural wrapping does not add paragraph gaps.

Automatic fixed and AI tags are paused throughout generation and writing. Saved tag preferences remain stored, the settings page explains the pause, and tags already present in the original stay unchanged. Existing Notes tags are never removed.

The model is instructed not to rewrite or repeat the draft, invent the user's history or motives, imply unsupported retrieval or verification, or treat instructions inside the draft as permission to act. Preferences can shape supplements but cannot replace the original-protection or output rules. This path performs no browsing; historical context is limited to the enabled Related History retrieval below.

An absent key, timeout, network failure, empty response, or wholly unusable output yields no AI section and no failure placeholder. The complete optional preparation, including related-history retrieval, provider queues, and AI generation, has a five-minute deadline from the start of background preparation. On timeout, Jotway cancels that work and continues with the original text without waiting for cancellation to finish. Late AI results are ignored; they never create another note or append to the saved note. Notes does not prewarm history retrieval or AI supplementation while the user is typing, and confirmation does not wait for either service. The deadline bounds optional work; the subsequent Notes write still waits for a confirmed result. No tag field is accepted in the generation protocol.

Notes retains the existing AI enable preference, including a saved off state and the current enabled-by-default behavior when unset. Supplement preferences use a separate key. Legacy custom rewrite instructions remain stored but are not executed or copied into the new preference; saved new preferences survive reopening. Settings explains this change when a legacy style exists.

Background preparation uses the frozen action configuration, bounded deep request, and provider queue. Before confirmation, draft or configuration changes invalidate old plans. After confirmation, preference changes and index invalidation cannot prevent the original from being saved; invalidated optional work is skipped. Cancellation of the submission still prevents writing, while cancellation within an optional service only skips the supplement. A changed destination invalidates the pending write and triggers the normal failed-submission recovery. Cancellation and destination validity are checked again after folder readback, immediately before the create event.

## Recent saved documents

Only confirmed successful Notes outcomes with a valid note identifier populate recent-document references. New notes and daily grouped appends use the same rule: a repeated ID moves to the front with its latest confirmed save time, and only three unique references remain. The single footer entry is available after a confirmed save on the current local day; this condition does not delete older references or restrict browsing to today. Failed or uncertain outcomes, draft edits and other actions do not qualify. Startup never scans or backfills Notes history.

Opening the entry or navigating the lower detail card explicitly reads that document's current plaintext through the public Notes Apple Events interface. It does not use a saved body snapshot, Related History, embeddings or a model. The session cancels and invalidates previous reads when selection changes; loading and failure do not prevent navigation. Closing, hiding or changing mode discards transient content. The `notes.recentSavedDocuments.v1` preference still stores only IDs and confirmed save times. See [Launcher appearance](../../openspec/specs/launcher-appearance/spec.md) for exact navigation and lifetime rules, and [Recent saved documents](../product/overview.md#recent-saved-documents) for the product flow.

## Initial titles and same-day recovery

Every newly created note resolves a title from its first complete original through the fast text capability, independent of grouping, AI supplementation and Related History. A valid classifier `new` title is reused; appending preserves the existing title and makes no new title request. The fixed protocol asks for a specific semantic title in the original language, preferably 8–20 characters and at most 48. Validation rejects empty, multiline, oversized, HTML, date-prefixed and greeting-prefixed output. It never truncates the original to make a fallback title. Title requests contain no candidate history or generated supplements.

One title round permits at most three calls within 30 seconds including title/provider queueing and backoff, with each call capped at eight seconds. Backoff is one then three seconds, extended by a valid Retry-After only when it fits the remaining budget. Temporary network errors, 408, 429, 5xx, timeouts and invalid titles may retry. Authentication, balance, 400/422, unsupported-model or oversized-input errors pause until configuration changes. Cancellation, stale configuration and late results cannot be adopted. This retry policy belongs only to initial titles; it does not change other model consumers.

When a title remains unavailable, Jotway saves the complete original once under “标题待生成” for Chinese text or “Title pending” otherwise. The confirmed note retains its layout, first-entry identity, title state, completed background-round count, next attempt and non-secret fast-configuration version in the management ledger. Existing notes and pre-title snapshots do not acquire title tasks. Missing safety metadata still permits an original-only emergency save with a temporary title, but forbids automatic recovery for that note.

Pending work resumes only for the configured destination and current local day. Its durable schedule is one, five, fifteen, thirty, then thirty minutes; a restart does not reset it. A configuration change wakes paused same-day tasks. One coordinator serializes title request rounds globally and selects the earliest due eligible task, while pending/unknown external writes remain excluded. Cross-day tasks expire without changing yesterday's note. Disabling grouping, supplementation or history does not cancel title recovery; changing destination or fast credentials/binding invalidates prior results. Credential-change revisions persist as non-secret preference counters so the comparison survives restart.

Recovery generates outside the Notes write FIFO, then rejoins it to read and validate the latest note ID, destination, creation day, full body, permissions and attachment state. Only the still-pending title is replaced: all latest originals and generated regions remain byte-for-byte equivalent in the boundary. When the app's title span survives, all remaining HTML is retained exactly; otherwise complete verified plaintext is rendered and old link presentation may be unavailable. Appends and late supplement refreshes retain the current title. Confirmed title replacement has no second save notification and cannot restore an old draft. Unknown results, including cancellation after dispatch, retain the expected pending version and are read-reconciled without repeating the write. Manual edits fail closed.

Settings explains the independent title behavior, missing fast-model configuration and same-day recovery. Content-free title diagnostics distinguish request attempts/elapsed time/error class from confirmed title adoption and durable pending/paused/conflicted/expired states. They contain no note IDs, titles, original/generated text or credentials. Real Notes formatting, model title quality and external-editor races remain separate manual acceptance boundaries.

## Daily project grouping

Settings → Apps → Apple Notes provides an independent daily grouping switch, on when unset and preserving an explicit off state, plus Fast Model configuration status and a disclosure that today's candidate originals are sent for classification. It does not require Related History or AI supplementation. Turning it off restores the ordinary path above.

Only notes created by this feature today in the configured destination are managed. Existing notes are not taken over by title, and older notes are never modified even if edited today. The frozen fast chain compares new text with complete ordered originals from verified candidates, preferring to append when the originals support a reasonable, specific and useful shared work or research topic. Short descriptions, parent/child topics, adjacent subtopics, different tools or repositories, and a narrower existing title do not alone require a new note. Browser testing, Agent testing and testing-tool selection can share an automation-testing research topic without an explicitly repeated goal. “Project” means the user's work, not a reference repository's identity. Different concerns or opposing views within one effort stay together; explicitly different work and unrelated content do not merge under generic labels such as “technology.” With multiple relevant candidates, the best-supported candidate wins; only genuine ambiguity, no useful common topic, explicit work boundaries or unrelated multi-topic input causes semantic fallback. Missing credentials, invalid output, a returned-model mismatch, the 128 KiB request cap or a classification deadline still causes independent storage. Existing titles stay unchanged and no historical groups are merged. Nothing is split, silently truncated or moved later.

Each accepted submission has a 300-second grouping decision budget. FIFO queueing, pending reconciliation and initial candidate preparation can use at most 180 seconds, reserving a separate 120-second classification window that starts when candidates are ready and includes the model queue. One cross-day reselection shares the original overall deadline and uses at most its remaining time. Preparation or model timeout settles once and ignores late read/model results. An expired queued submission still waits for its safe FIFO turn before saving independently. These limits do not time out, bypass or retry a dispatched original write; uncertain outcomes retain their pending identity. Original confirmation and the later AI refresh use their existing independent rules; refresh retains its own 300-second limit.

The module-owned FIFO coordinator serializes ordinary and grouped original saves, title adoption and refresh writes. A managed note displays its stable topic title followed by each complete original in submission order, preceded by a separate `- HH:mm` line in the submission time zone. It has no standalone date line or displayed seconds/time-zone suffix. One blank line separates title/time, time/body and adjacent entries, in addition to all whitespace already in the original. Full timestamps, time zones, identities and sequence remain stored; entries in the same minute are distinct. Old-format boundaries remain readable; only otherwise-permitted current-day writes redraw the compact format, never reads or a historical batch migration. Intentional repeated submissions remain separate; recovery of the same submission does not append again. Date and time zone are rechecked before dispatch. A date change reselects current candidates, with at most one reclassification; old-day targets receive no update.

After the original is confirmed, optional assistance processes the full accumulated originals. Its history query prioritizes the latest entry within the existing 4,000-character query bound, excludes the current note and may read older notes within the existing authorized history scope. One shared AI Insights / Related Content tail is replaced, not accumulated. A new original cancels the older refresh and invalidates its revision. The refresh deadline is 300 seconds from scheduling, including preparation and queueing. Invalidated history, destination, day, configuration or body prevents adoption. Generation failure or timeout never restores an already-saved draft or emits another save notice.

When prior generated content remains after an append, a short notice gives its coverage time and says the latest ideas are not included. Successful replacement removes the notice; a valid empty response removes both the old tail and notice. Missing/failed/over-budget generation retains the stale tail; no prior result means no empty placeholder. Turning assistance off cancels its work while leaving grouping enabled; the next managed original write removes old generated content. Changing a switch alone does not rewrite Notes.

The coordinator retains a bounded in-memory cache of confirmed originals, title and generated tail, isolated by destination, local natural day and time zone. Its default text-payload budget is 16 MiB, with least-recently-used eviction; it is not a process-memory guarantee. Evicted or oversized entries are recovered completely for the current submission, so eviction never reduces the candidate set or truncates text. Restart starts cold. Scope changes and disabling grouping clear the cache; cancelling only optional AI work retains valid originals. Confirmed original writes, refresh writes and pending reconciliation update the complete cached revision. The cache adds no persistent body copy and is independent of Related History.

Candidates come from the local same-day management ledger. Cold entries receive one full read. Warm entries check only ID, actual folder, creation/modification dates, lock and sharing state through the public per-property interface; they do not read title, body, HTML or attachments. Arbitrary-ID batch reads are not enabled. Changed state triggers full recovery and boundary validation. Temporary service/permission/read failures end that preparation attempt without permanently marking the note conflicted or classifying an incomplete candidate set. Confirmed edits, moves, deletion or inaccessible note state protect the affected note. Metadata is only a cache hint, including when external edits share its timestamp precision.

Content-free grouping diagnostics correlate queue/preparation/model time, final-validation/readback I/O time, actual Apple Event read-send counts, candidate/cache counts, model placement, final save kind and fallback reason. Reads are counted at the transport send boundary, separately from writes and model calls. Reports contain no Notes IDs, titles, original text, model reasons or credentials. Late results cannot alter a completed report.

Before update, the public Apple Events adapter verifies the note ID, destination, creation day, readable unlocked/unshared state, attachment absence and exact full-body version, then sets the body and reads it back. This adapter guard is the sole final full pre-read; the coordinator does not repeat it. Managed confirmation returns a coherently checked body and metadata for cache installation, and managed ordinary create uses the same complete confirmation contract. Detected edits, moves, deletion, attachments, locks or sharing protect the old note; a new original gets an independent note. A changed destination invalidates the original write instead of silently changing folders. Metadata storage failure before dispatch falls back to an independent original-only save. Unknown create/update outcomes retain a pending identity and expected fingerprint; later complete readback can confirm them, but an unproven outcome never triggers a blind repeat. Restart recovery only resumes valid current-day work.

Management stores hashes and identity metadata, not another body copy. Full-version and per-region verification separates original entries from titles, times, stale notices and generated content during classification and indexing. HTML attribute removal is tolerated only if complete plaintext still matches the ledger. Whitespace changes beyond normalized line endings fail closed. If Notes removes generated HTML markup, retained stale content can be recovered as plaintext and source links may lose clickability until regenerated. Public read-then-write is not an atomic compare-and-swap with external editors; an external edit between the last check and the write remains a race. Real Notes normalization, update/rendering and model quality require separate real-environment evaluation.

## Success and failure

Success requires a confirmed note identifier; managed writes also require the expected complete body and folder readback. Original success and optional refresh failure are separate outcomes. Folder reads preserve the distinction between permission refusal (`-1743`), an empty folder list, a missing destination, and a Notes launch failure. Permission errors are not displayed as an empty folder list.

Missing destination, empty content, permission failure, or an unconfirmed write response returns an error to the panel. The panel restores the original text unless a new draft already exists, in which case it retains the failed submission separately. A permission failure also makes Notes configurable again without erasing its saved destination. Jotway does not automatically retry a write whose outcome may be unknown.

## Boundaries

- Jotway does not keep a second original-text copy for provenance. The origin ledger holds note IDs, format versions and whitespace-normalized original/generated-tail hashes and lengths; the optional search index separately holds derived plaintext.
- Configuring Notes is separate from submitting the draft.
- Permission details belong to the Notes module; the launcher hosts a generic setup flow.

## Related History

Settings → Apps → Apple Notes has a Related History switch, enabled when no saved preference exists, and an Embedding Service card. Existing explicit off values remain effective. Save a separate Alibaba Cloud key there; Test Connection sends a fixed sample only. Once Notes access and the key are ready, the shared index starts automatically without an initial Index Notes action. Startup, successful authorization, key saving, re-enabling and returning from System Settings check readiness. Passive checks never request permission; Allow Notes Access is shown only when access is missing. Ordinary typing and prewarming do not start indexing. The scope defaults to all accessible accounts/folders and preserves any saved custom selection, including an empty scope. Choose Folders explicitly reads folder names and can request access.

Configure your own HTTPS DashScope workspace embedding URL and matching API key in Apple Notes settings. No workspace URL or credentials ship with the app. Saving the URL performs no connection test; clearing it disables embedding readiness. Changing it invalidates in-flight work, and an existing index must be cleared and rebuilt before reuse. The URL follows the [official DashScope embedding API](https://www.alibabacloud.com/help/en/model-studio/text-embedding-synchronous-api).

Selected plaintext fragments and queries go to the configured DashScope endpoint using `qwen3.7-text-embedding`, 1024-dimensional dense vectors. A separate local `notes-index.sqlite` holds derived text and vectors. No Notes private database, UI scraping, cloud vector database or cross-device vector synchronization is used. Notes account synchronization remains the user's responsibility.

An enabled, authorized index with a saved key refreshes at application startup and every ten minutes unless paused. Only one sync runs at a time; changing configuration cancels the old sync and schedules at most one refresh using the latest configuration. Cancel Sync immediately shows that it is stopping, preserves completed batches and persists a pause. An in-flight Notes Apple Event can take up to its 30-second timeout to return. Clear Index cancels old work and also pauses automatic rebuilding. Returning to the app or restarting keeps the pause; Resume Indexing or explicitly re-enabling Related History permits work again. Old saved started=false values from Clear Index also remain paused. Clearing does not delete Notes or operation records. Folder discovery reports the number of folders found and skips default-save-location queries. During metadata scanning, the page shows the current folder and discovered note count with indeterminate progress; it does not report an unknown total as zero. After scanning, it reports processed notes after every note, the current reading/embedding/saving stage, and elapsed seconds. The page also reports searchable notes, locked, unreadable, pending/empty and failed notes, unextracted attachment count and last successful sync. Attachments, OCR, PDF and image contents are not extracted. Empty body and empty HTML are reported as empty or not yet synced; the public interface cannot prove which state caused them.

Metadata scans use public Notes collections, including nested folders. Six metadata fields are read from bounded ranges of up to 40 notes, with source IDs checked again before accepting each batch and the folder count checked afterward. Collection reads avoid fetching bodies or all properties. Unsupported collection reads fall back to per-note metadata reads with progress; permission failures and timeouts do not trigger that retry. These are local Apple Events, not a change feed or server pagination API. Body reads are sequential and changed note metadata or an outdated processing version causes a reread. Paragraph hashes reuse embeddings while preserving each source ID. A complete note replacement and its vectors publish atomically in batches of up to four changed notes. Only folders whose metadata enumeration completed are eligible for deletion reconciliation; an unavailable account/folder is not proof of deletion. Such older data is retained until its folder can be reconciled or the user clears the index. Notes normally excludes Recently Deleted from its scripting collections; exposed English and Simplified/Traditional Chinese trash names are also excluded. Other system-language exposure requires manual verification.

When Add Extra Ideas is enabled, confirmed saves retrieve up to ten distinct old-note candidates within the shared excerpt budget and ask the selected deep capability for zero to five useful historical associations plus zero to three useful additions. Tag-only, short generic and original-duplicate excerpts are filtered before the candidate limit. Invalid early matches do not consume source slots; later valid excerpts from the same source remain eligible. The parser recovers JSON objects or arrays from Markdown fences and surrounding prose, tolerates trailing commas, omitted/null sections, extra metadata, string items and single-item objects, and accepts common `insights`, `related_content`/`relatedContent`, `content`, and source-ID casing variants. A direct text answer can supply insights without history. Generated paragraphs have whitespace normalized; the original draft is unaffected. Extra fields, including tags and insight evidence, are ignored rather than displayed. Invalid, oversized and duplicate entries are skipped independently, so one bad entry cannot discard valid siblings or the other section. The first three valid insights and five valid distinct sources are kept; invalid early entries do not consume those slots.

Historical associations still require a source ID from this retrieval, a valid application-constructed link and an 8–160 character evidence span that matches that source after whitespace normalization. A literal source quote can supply its own evidence when the separate field is omitted. Missing or invalid evidence and unknown source IDs discard only that association. Repeated sources retain the first valid association. Titles and identities come from the retrieved source, never model metadata. Malformed structured data is not saved as raw JSON. Completely unusable output falls back to the original; intentionally empty output omits the generated sections. The parser accepts at most 65,536 UTF-8 bytes, while the generation prompt requests at most 8,192. The renderer repeats cardinality, length and duplicate checks for all processors, including between supplement items. Each section remains inside its existing generated-region boundary.

Generation instructions require a substantive response to the current question, complementary evidence from multiple sources when available, uncertainty for inferences and completion status, and omission of unrelated history or non-incremental advice. A note with several ideas still counts as one source. History explains the supporting context; the AI section adds analysis rather than repeating that summary. A valid evidence span does not prove the model's interpretation or semantic relevance; paraphrase duplication, insight quality and unsupported inferences still require real-model evaluation. No hit or ordinary retrieval failure omits history. An observed index change during optional preparation discards the supplement without blocking the original. With grouping disabled, one confirmation performs one create with no later append. Grouping instead confirms one original create/append and can later replace that revision’s generated section. Content-free diagnostics distinguish retrieved candidates, validated item/history counts and the content actually carried by the create request. Valid empty output, history-only output, protocol rejection, disabled assistance, missing configuration, service errors, timeout and stale work have separate results. Provenance failure or renderer filtering is recorded at adoption; adoption does not prove the Notes create succeeded. Late provider completion cannot replace the preparation outcome.

Search History uses the same candidate policy as confirmed saves: enter a question, inspect candidate count, source title, modified date and excerpt, then Open in Notes. It shows searchable, pending and failed counts from the same scoped index snapshot. Pending, failed or excluded records, or the absence of a completed sync, produce an incomplete-results notice; these counts never establish full-library coverage. AI may select fewer sources for the saved history. Changing the query, scope or index version invalidates both results and their coverage summary. A retrieval failure remains distinct from a successful zero-hit search. Saved history links source titles using `jotway://notes/open?id=…`, with the real source note ID encoded as a URL query value. The registered Jotway URL handler validates the link and uses the same public Notes `show` command; opening does not require history indexing, an embedding service or a network request. Missing sources and permission failures produce a local error. It does not construct guessed `notes://` links or create shared notes.

Source links require a packaged Jotway version with this URL handler on the same Mac. They are not Apple-native cross-device note links: local note IDs and timestamps are observations from this Mac, not cross-device stable identifiers or real-time change guarantees. Old saved notes are not rewritten. Notes ultimately controls HTML import and link presentation; supported formats and integration limits are recorded in the [formatting reference](../development/apple-notes-formatting-research.md).

Chunking splits on blank-line paragraphs and limits each chunk to 1,200 characters / 4,096 UTF-8 bytes, without overlap. Notes over 2 MB plaintext / 4 MB HTML or 2,000 chunks fail processing. Extraction excludes AI, history, source information and legacy generated tags. An intact original HTML region preserves user-written text, including similar-looking headings and tags. When neither an intact original region nor a verified local fingerprint is available, exact whole-line legacy English/Chinese generated headings retain their tail-truncation fallback, including a heading at the start of a generated-only note. New headings (“AI 洞察”, “相关内容”, “AI Insights”, “Related Content”) alone are ordinary user text and never trigger truncation. A complete new divider line followed by a blank line and one of these headings instead signals an unverified boundary: extraction skips the note as ambiguous, even if a legacy heading also appears elsewhere. An intact original region or a complete known fingerprint takes precedence over this display signal. Surviving but damaged markers are ambiguous rather than permission to embed the full note. HTML-only bodies use conservative text conversion; plaintext and HTML are checked for disagreement when the original marker survives.

Before each production create, the local origin ledger records only format version and hashes/lengths of the original and generated tail; the confirmed note ID is attached afterward. The generated tail includes the divider, headings, all additions, source prefixes, title decoration and arrows. The new layout retains origin format version 2 and the existing extraction version; it requires no schema migration, index reset or rewrite of saved notes. Pending fingerprints cover uncertain writes; cancellation, stale destinations and definite non-writes discard their pending record. Confirmed and uncertain write outcomes survive cancellation arriving after dispatch. If staging provenance fails, optional generated material is dropped and only the original is saved. After HTML attributes disappear, both original and generated-tail fingerprints must account for the complete whitespace-normalized body. A shared prefix never identifies an external note. A tail-only match to a pending write skips that read as ambiguous without assigning permanent ownership. An intact original marker must match the complete stored original, agree with plaintext and leave no unaccounted body changes, including paragraphs added outside the marker. Edited originals or unmarked edited tails that no longer satisfy these boundaries are reported as “Original boundary unclear — skipped”; this deliberately sacrifices recall instead of silently truncating user text. Recognizable legacy notes acquire an origin record when read. Known ambiguous identities, including unverified new-format boundaries, remain protected if later edits remove the display markers. Clear Index retains these non-content safety records. External copies that lose all markers, recognizable headings and local identity cannot always be classified; unresolved writes followed by edits to both original and generated tail can also lose recognition.

Processing version 3 atomically removes prior-version vectors and marks sources for reprocessing before search can use them. The next permitted sync rereads even unchanged ready metadata and rebuilds under the new extraction contract. No old Notes body is rewritten. Provider/model/dimension changes still require explicit Clear Index and Resume Indexing. Processing migration never overrides an explicit off setting or restarts a cleared index; cancelled work cannot publish new batches. Use Refresh for an active index or Resume Indexing after pausing or clearing. Skipped boundaries and awaiting-extraction status are visible in Related History.

Retrieval uses cosine exact KNN in sqlite-vec v0.1.9, with folder filtering inside each KNN query before merging candidates. At most 40 candidates per folder are considered, then duplicate text and repeat note IDs are removed. After content filtering and source/text deduplication, at most ten excerpts of 400 characters and 8,000 aggregate UTF-8 bytes reach generation; the byte budget can produce fewer than ten. Counts distinguish raw chunks, distance-qualified chunks, eligible distinct sources and delivered candidates. Equal distances use stable chunk identity ordering. The initial distance cutoff is 0.35 (cosine similarity at least 0.65); synthetic same-direction and orthogonal examples check the filter, but real recall needs calibration after the user configures a key. Similarity is not factual confidence.

## Model capability ownership

Notes receives `ModelConfiguration` from the app. Titles and daily classification use fast (Flash → Kimi Code Highspeed by default); supplementation uses deep (Pro → Kimi Code). Both chains can be reversed or have no fallback. Each accepted save freezes its text invocations, including queued classification and later supplement work. Candidate/JSON validation, original-first writes and Notes revision guards remain business-owned. Only model timeout/disconnect, 408/429 and 5xx can trigger one fallback, without preparing candidates or repeating a Notes write. Classification retains 120 seconds, separate from the 180-second candidate-preparation budget. Supplement generation receives the remainder of its existing 300-second optional preparation/refresh deadline, including retrieval. Cancellation or invalidation prevents fallback and adoption; invalid output never starts a new attempt. Embedding is a separate typed capability with the existing compatibility identity; incompatible profiles block retrieval/sync without clearing the index.

## Web links in original text

A complete, valid HTTP/HTTPS URL on its own line is rendered as an explicit anchor inside the original region. Its full query and fragment, visible text and surrounding whitespace are preserved; other Markdown remains literal. The same renderer serves ordinary create, daily append, supplement refresh and retained generated sections. Web attribution remains original draft text even when AI is disabled or fails. Generated history links continue to use the separate Notes deep-link rules above. Chrome Source supplies editable attribution only when explicitly enabled; it neither selects Notes nor attaches hidden metadata.
