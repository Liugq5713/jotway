# Apple Notes action

> Role: **Current**

Notes is the only bundled storage fallback. Today/weekly reviews use their own folder scope and read authorized originals on demand, independently of the save destination.

Apple Notes is the preferred storage fallback once a destination is configured and no known permission failure prevents execution. When it needs configuration, the panel offers Set Up Notes as an explicit target and as the fallback when no other storage action can execute.

## Routing

Explicit phrases such as “记一下”, “存备忘录”, “save to notes”, and “take a note” can match locally, including when Notes needs setup. A user can select Notes directly from the target menu. Routing does not request a model; setup is never an execution candidate or a prewarmed action.

The `@` picker offers input templates and only edits the draft. Old `@notes` text is literal, including when Notes is explicitly selected. Before saving, Jotway preserves the complete original draft, its leading text and whitespace; it does not remove an action marker.

Without a stronger explicit target, bundled keyword or qualified local application match, Notes is the only bundled storage fallback. If it is not ready, Set Up Notes opens configuration. An unavailable explicit target retains its error instead of silently switching to Notes.

## Authorization and configuration

Pressing Enter or Command+Enter in the editor with Set Up Notes selected opens a single configuration window with an Allow Access button and an explanation of the default destination. Clicking Allow Access makes the Apple Events request that can trigger the macOS consent dialog. Opening the setup window or action settings page, typing, rendering the panel, background recognition, and action prewarming do not request Notes permission.

After authorization, Jotway keeps the saved destination when it is still available. Otherwise, it selects the default folder in the default Notes account, then another account's default folder, then the first exposed folder if no account default is available. Successful launcher setup completes automatically. Settings → Apps shows the selected destination and offers Change… to open the optional folder picker; the launcher setup window has no picker. Authorization and destination selection do not create a test note, and no verification step is required.

The draft, selection, and draft identity are retained while recognition is paused. Repeated confirmation focuses the existing configuration window. Completing, cancelling, or closing configuration returns to the same draft; successful configuration selects Notes and waits for another Enter before saving. A stale configuration callback cannot replace a newer draft or take its focus. Setup does not clear the draft, play a submission animation, or record action execution or model-adoption feedback.

Permission refusal and revocation retain the selected destination and direct the user to System Settings → Privacy & Security → Automation → Jotway → Notes. When authorization or the saved destination needs repair, settings and launcher setup offer Open System Settings and Allow Access Again. They do not reset permissions or promise that macOS will show the consent dialog again. A successful authorized read clears the known permission-failure state.

## Execution

Ordinary saves and grouped saves retain the complete frozen original. Saving never requests AI insights, waits for a supplement deadline, or schedules a later generated-content write.

1. On confirmation, freeze the complete original and destination, reject whitespace-only content, then clear the accepted draft and hide the panel.
2. Resolve an independent initial title (or reuse a valid grouping title). If unavailable, save under the pending-title placeholder and retain the same-day guarded title recovery rules.
3. Persist the complete non-content boundary fingerprints, create or append through the serialized Notes adapter, and require the expected identifier, folder and complete readback before confirming success.

Closing or reopening the panel does not cancel an accepted submission. Destination validity and submission cancellation are checked before dispatch. Preference changes cannot rewrite the frozen original or silently change its destination. Unknown write outcomes remain pending for read-only reconciliation rather than being sent again.

The ordinary note contains its separate title, a blank line and the complete original exactly once. It preserves the first line, action-like markers, leading/trailing whitespace, blank lines, tabs, indentation, repeated lines, literal Markdown, code, URLs and escaped HTML. Line endings may be normalized and a final newline may be appended. It has no grouped timestamp. Complete boundaries exclude titles and display metadata from later original extraction.

After confirmed saving, the optional completion notice follows [completion feedback](../product/overview.md#completion-feedback). Acceptance or title generation alone is not success. Clicking the notice activates Notes without another save or a promise to select the created note.

The former Add Extra Ideas switch, preference editor and rewrite notice are removed. Existing enable/prompt/style values remain stored and inactive; they neither trigger requests nor invalidate active model configuration. No migration clears settings or credentials. Fixed and AI tags remain paused, and original user-written tags remain unchanged.

## Recent saved documents

Only confirmed successful Notes outcomes with a valid note identifier populate recent-document references. New notes and daily grouped appends use the same rule: a repeated ID moves to the front with its latest confirmed save time, and only three unique references remain. The single footer entry is available after a confirmed save on the current local day; this condition does not delete older references or restrict browsing to today. Failed or uncertain outcomes, draft edits and other actions do not qualify. Startup never scans or backfills Notes history.

Opening the entry or navigating the lower detail card explicitly reads that document's current plaintext through the public Notes Apple Events interface. It does not use a saved body snapshot or a model. The session cancels and invalidates previous reads when selection changes; loading and failure do not prevent navigation. Closing, hiding or changing mode discards transient content. The `notes.recentSavedDocuments.v1` preference still stores only IDs and confirmed save times. See [Launcher appearance](../../openspec/specs/launcher-appearance/spec.md) for exact navigation and lifetime rules, and [Recent saved documents](../product/overview.md#recent-saved-documents) for the product flow.

## Initial titles and same-day recovery

Every newly created note resolves a title from its first complete original through the fast text capability, independent of grouping. A valid classifier `new` title is reused; appending preserves the existing title and makes no new title request. The fixed protocol asks for a specific semantic title in the original language, preferably 8–20 characters and at most 48. Validation rejects empty, multiline, oversized, HTML, date-prefixed and greeting-prefixed output. It never truncates the original to make a fallback title. Title requests contain no candidate history or generated supplements.

One title round permits at most three calls within 30 seconds including title/provider queueing and backoff, with each call capped at eight seconds. Backoff is one then three seconds, extended by a valid Retry-After only when it fits the remaining budget. Temporary network errors, 408, 429, 5xx, timeouts and invalid titles may retry. Authentication, balance, 400/422, unsupported-model or oversized-input errors pause until configuration changes. Cancellation, stale configuration and late results cannot be adopted. This retry policy belongs only to initial titles; it does not change other model consumers. Jotway AI activation uses one attempt and pauses automatic title retries after any failure, including uncertain network outcomes, to avoid repeated quota charges.

When a title remains unavailable, Jotway saves the complete original once under “标题待生成” for Chinese text or “Title pending” otherwise. The confirmed note retains its layout, first-entry identity, title state, completed background-round count, next attempt and non-secret fast-configuration version in the management ledger. Existing notes and pre-title snapshots do not acquire title tasks. Missing safety metadata still permits an original-only emergency save with a temporary title, but forbids automatic recovery for that note.

Pending work resumes only for the configured destination and current local day. Its durable schedule is one, five, fifteen, thirty, then thirty minutes; a restart does not reset it. A configuration change wakes paused same-day tasks. One coordinator serializes title request rounds globally and selects the earliest due eligible task, while pending/unknown external writes remain excluded. Cross-day tasks expire without changing yesterday's note. Disabling grouping or history does not cancel title recovery; changing destination or fast credentials/binding invalidates prior results. Credential-change revisions persist as non-secret preference counters so the comparison survives restart.

Recovery generates outside the Notes write FIFO, then rejoins it to read and validate the latest note ID, destination, creation day, full body, permissions and attachment state. Only the still-pending title is replaced: all latest originals and generated regions remain byte-for-byte equivalent in the boundary. When the app's title span survives, all remaining HTML is retained exactly; otherwise complete verified plaintext is rendered and old link presentation may be unavailable. Appends retain the current title. Confirmed title replacement has no second save notification and cannot restore an old draft. Unknown results, including cancellation after dispatch, retain the expected pending version and are read-reconciled without repeating the write. Manual edits fail closed.

Settings explains independent titles, saving with a pending title and possible same-day recovery. Missing model configuration is covered by one shared setup hint for titles, grouping and reviews. Content-free title diagnostics distinguish request attempts/elapsed time/error class from confirmed title adoption and durable pending/paused/conflicted/expired states. They contain no note IDs, titles, original/generated text or credentials. Real Notes formatting, model title quality and external-editor races remain separate manual acceptance boundaries.

## Daily project grouping

Settings → Apple Notes provides an independent daily grouping switch, on when unset and preserving an explicit off state, plus a disclosure that new ideas and today's candidate originals are sent for classification. When the model is configured, the page shows no AI setup status or AI Services shortcut. When configuration is missing, one shared hint links to AI Services and explains that notes can still be saved separately with a pending title. It does not request saved AI supplements. Turning grouping off restores the ordinary path above.

Only notes created by this feature today in the configured destination are managed. Existing notes are not taken over by title, and older notes are never modified even if edited today. The frozen fast invocation compares new text with complete ordered originals from verified candidates, preferring to append when the originals support a reasonable, specific and useful shared work or research topic. Short descriptions, parent/child topics, adjacent subtopics, different tools or repositories, and a narrower existing title do not alone require a new note. Browser testing, Agent testing and testing-tool selection can share an automation-testing research topic without an explicitly repeated goal. “Project” means the user's work, not a reference repository's identity. Different concerns or opposing views within one effort stay together; explicitly different work and unrelated content do not merge under generic labels such as “technology.” With multiple relevant candidates, the best-supported candidate wins; only genuine ambiguity, no useful common topic, explicit work boundaries or unrelated multi-topic input causes semantic fallback. Missing credentials, invalid output, a returned-model mismatch, the 128 KiB request cap or a classification deadline still causes independent storage. Existing titles stay unchanged and no historical groups are merged. Nothing is split, silently truncated or moved later.

Each accepted submission has a 300-second grouping decision budget. FIFO queueing, pending reconciliation and initial candidate preparation can use at most 180 seconds, reserving a separate 120-second classification window that starts when candidates are ready and includes the model queue. One cross-day reselection shares the original overall deadline and uses at most its remaining time. Preparation or model timeout settles once and ignores late read/model results. An expired queued submission still waits for its safe FIFO turn before saving independently. These limits do not time out, bypass or retry a dispatched original write; uncertain outcomes retain their pending identity. Original confirmation retains its own guarded write/readback rules; no supplement refresh is scheduled.

The module-owned FIFO coordinator serializes ordinary and grouped original saves, title adoption. A managed note displays its stable topic title followed by each complete original in submission order, preceded by a separate `- HH:mm` line in the submission time zone. It has no standalone date line or displayed seconds/time-zone suffix. One blank line separates title/time, time/body and adjacent entries, in addition to all whitespace already in the original. Full timestamps, time zones, identities and sequence remain stored; entries in the same minute are distinct. Old-format boundaries remain readable; only otherwise-permitted current-day writes redraw the compact format, never reads or a historical batch migration. Intentional repeated submissions remain separate; recovery of the same submission does not append again. Date and time zone are rechecked before dispatch. A date change reselects current candidates, with at most one reclassification; old-day targets receive no update.

After an append, any verified legacy generated regions and their existing trailing coverage metadata remain intact after all originals. No new stale notice, generated heading, insight or related-content section is created. Classification receives only recovered original entries. Restart and configuration changes resume eligible title recovery only, never supplement generation.

Legacy generated content is preserved on a permitted same-day append regardless of saved retired preferences. Complete boundary verification governs recovery; visible “AI Insights” wording alone is never permission to split or discard content. Trusted surviving generated HTML keeps existing source links. If markup cannot be verified but the complete plaintext boundary matches, all old text and coverage metadata survive as escaped plaintext; links are not reconstructed or regenerated.

The coordinator retains a bounded in-memory cache of confirmed originals, title and generated tail, isolated by destination, local natural day and time zone. Its default text-payload budget is 16 MiB, with least-recently-used eviction; it is not a process-memory guarantee. Evicted or oversized entries are recovered completely for the current submission, so eviction never reduces the candidate set or truncates text. Restart starts cold. Scope changes and disabling grouping clear the cache. Confirmed original/title writes and pending reconciliation update the complete cached revision. The cache adds no persistent body copy and is independent of reviews.

Candidates come from the local same-day management ledger. Cold entries receive one full read. Warm entries check only ID, actual folder, creation/modification dates, lock and sharing state through the public per-property interface; they do not read title, body, HTML or attachments. Arbitrary-ID batch reads are not enabled. Changed state triggers full recovery and boundary validation. Temporary service/permission/read failures end that preparation attempt without permanently marking the note conflicted or classifying an incomplete candidate set. Confirmed edits, moves, deletion or inaccessible note state protect the affected note. Metadata is only a cache hint, including when external edits share its timestamp precision.

Content-free grouping diagnostics correlate queue/preparation/model time, final-validation/readback I/O time, actual Apple Event read-send counts, candidate/cache counts, model placement, final save kind and fallback reason. Reads are counted at the transport send boundary, separately from writes and model calls. Reports contain no Notes IDs, titles, original text, model reasons or credentials. Late results cannot alter a completed report.

Before update, the public Apple Events adapter verifies the note ID, destination, creation day, readable unlocked/unshared state, attachment absence and exact full-body version, then sets the body and reads it back. This adapter guard is the sole final full pre-read; the coordinator does not repeat it. Managed confirmation returns a coherently checked body and metadata for cache installation, and managed ordinary create uses the same complete confirmation contract. Detected edits, moves, deletion, attachments, locks or sharing protect the old note; a new original gets an independent note. A changed destination invalidates the original write instead of silently changing folders. Metadata storage failure before dispatch falls back to an independent original-only save. Unknown create/update outcomes retain a pending identity and expected fingerprint; later complete readback can confirm them, but an unproven outcome never triggers a blind repeat. Old `pending.refresh` records still decode. A matching complete readback can confirm their stored expected snapshot; unmatched records remain unresolved and exclude the affected note from further writes. No code creates or replays a refresh operation. Restart recovery only resumes eligible current-day titles.

Management stores hashes and identity metadata, not another body copy. Full-version and per-region verification separates original entries from titles, times, stale notices and generated content during classification and indexing. HTML attribute removal is tolerated only if complete plaintext still matches the ledger. Whitespace changes beyond normalized line endings fail closed. If Notes removes generated HTML markup, retained stale content can be recovered as plaintext and source links may lose clickability and are never regenerated. Public read-then-write is not an atomic compare-and-swap with external editors; an external edit between the last check and the write remains a race. Real Notes normalization, update/rendering and model quality require separate real-environment evaluation.

## Success and failure

Success requires a confirmed note identifier; managed writes also require the expected complete body and folder readback. A failed title round cannot undo a confirmed original save. Folder reads preserve the distinction between permission refusal (`-1743`), an empty folder list, a missing destination, and a Notes launch failure. Permission errors are not displayed as an empty folder list.

Missing destination, empty content, permission failure, or an unconfirmed write response returns an error to the panel. The panel restores the original text unless a new draft already exists, in which case it retains the failed submission separately. A permission failure also makes Notes configurable again without erasing its saved destination. Jotway does not automatically retry a write whose outcome may be unknown.

## Boundaries

- Jotway does not keep a second original-text copy for provenance. The origin ledger holds note IDs, format versions and whitespace-normalized original/generated-tail hashes and lengths; no search index stores derived plaintext.
- Configuring Notes is separate from submitting the draft.
- Permission details belong to the Notes module; the launcher hosts a generic setup flow.

## Notes Review and original boundaries

Today and weekly reviews are explicit, read-only requests over today (local midnight through the request time) or the last 7 days of modification times. The review header shows both periods as segmented tabs, with the active period highlighted. They require an existing Notes grant and the active text model. Notes Review has its own switch and all-folders/custom-folder scope in Apple Notes settings; an existing history scope is retained without widening it. No background indexing, vector generation, related-note search or embedding configuration remains.

A request reads public Notes metadata in scope, selects at most 60 of the newest modified notes, extracts verified original text and sends at most 4,000 characters per note to the active text model. Locked, unreadable, empty or ambiguous originals are skipped; skipped sources, attachment content, missing selected folders, truncation or a 60-note limit produce a coverage notice. Metadata/permission failures and a wholly failed nonempty read are errors, not cacheable empty results. Review does not request permission implicitly, write Notes, or change the draft. Completed weekly/monthly results have separate six-hour in-memory caches; refresh rereads Notes. Closing, changing scope or losing permission cancels pending results.

`NotesOriginStore` retains the existing `notes-index.sqlite` path solely for original/generated boundary fingerprints. Its migration drops old source, chunk, vector and index-state tables and vacuums the cache, preserving original and daily-origin ledgers. It does not retain note bodies. The sqlite-vec library remains only to open and drop legacy virtual tables; no embedding requests or search queries can execute. Old service preferences and credential files are not read by the application.

Before writes, the ledger stages hashes and lengths of originals and generated tails and attaches the confirmed Notes ID afterward. Pending fingerprints protect uncertain writes. Generated additions are omitted if provenance cannot be staged. Verified boundaries and intact original markers exclude generated material from reviews; edited or inconsistent boundaries are skipped rather than treated as user evidence. Existing saved notes and their source links are not rewritten. Existing `jotway://notes/open` links still open the exact stored source ID through the public Notes interface.

## Model capability ownership

Notes receives `ModelConfiguration` from the app. A stored Jotway code routes titles and classification to hosted Flash and reviews to hosted Pro. Without a code, retained text features share one personal Claude or OpenAI-compatible model. No backup model, embedding capability or supplement invocation is exposed. Candidate/JSON validation, original writes and revision guards remain business-owned. Classification retains its 120-second model window and separate 180-second preparation budget; title retry and review streaming rules are unchanged.

## Web links in original text

A complete, valid HTTP/HTTPS URL on its own line is rendered as an explicit anchor inside the original region. Its full query and fragment, visible text and surrounding whitespace are preserved; other Markdown remains literal. The same renderer serves ordinary create and daily append. Web attribution remains original draft text regardless of model availability. Existing saved history links continue to use the Notes deep-link handler. Chrome Source supplies editable attribution only when explicitly enabled; it neither selects Notes nor attaches hidden metadata.

Service credentials are configured once in AI Services, linked from Notes grouping only when configuration is missing. Writing Preferences retains automatic draft responses and general instructions. The Notes Add Extra Ideas controls, preference editor and legacy rewrite notice are removed; their old values remain stored and inactive.
