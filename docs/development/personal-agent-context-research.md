# Personal Agent 上下文策略研究

> Role: **Reference**
> 调研日期：2026-10-10

Personal Agent 的上下文选择需要同时考虑问题范围和资料规模。小型资料集合可以直接进入上下文；具体事实适合定向检索；跨资料的整体认识需要更广的覆盖或分层摘要。下面是一手技术资料中的不同路径，并非业界统一架构；针对 Jotway 的应用建议不代表当前实现。

## 三种有来源支持的路径

| 路径 | 一手资料中的做法 | 适用边界 |
|---|---|---|
| 完整上下文 | Anthropic 在 2024 年 Contextual Retrieval 文章中说明，小型知识库可以整体放入提示词，并通过提示缓存降低重复处理开销 | 文中的 200,000 tokens 属于当时 Claude 的说明，不能当成所有模型、任务的安全阈值。[原文](https://www.anthropic.com/engineering/contextual-retrieval) |
| 定向检索 | 同文用语义检索和 BM25 关键词检索合并去重，再用 reranker 对候选评分，选出回答所需内容 | 适合存在具体实体、概念或事实线索的问题；索引片段应保留必要文档背景，单纯切片会丢失对象和日期。[原文](https://www.anthropic.com/engineering/contextual-retrieval) |
| 全局摘要 | Microsoft GraphRAG Global Search 用预生成的社区摘要覆盖资料主题，对摘要分批生成与问题有关的要点，再筛选、汇总回答 | 官方文档直接指出，全库主题问题通常缺少足以引导向量搜索的线索；摘要层级越细，回答可能更全面，但耗时和模型资源也会增加。[官方文档](https://microsoft.github.io/graphrag/query/global_search/) |

GraphRAG 的可借鉴点是先建立覆盖全局的表示，再回答全局问题。由此不能推出小型 Personal Agent 必须建设知识图谱；分时段或分主题的摘要也值得作为较简单的候选方案评估。

已经上线的产品也采用按规模切换的方式。Claude Projects 官方说明，项目知识接近或超过上下文限制时会自动启用 RAG；资料量降回阈值以下时，可以切回基于上下文的处理。这提供了直接产品实例，但其质量宣传不能代替 Jotway 自己的效果验证。[产品文档](https://support.claude.com/en/articles/11473015-retrieval-augmented-generation-rag-for-projects)

## 全量上下文与 RAG 的研究边界

《Retrieval Augmented Generation or Long-Context LLMs?》在其 2024 年选定模型和公开数据集上发现：资源充分时，长上下文的平均表现较好，RAG 的计算成本更低。其失败分析包括宽泛问题、隐含问题和需要多步获取线索的问题；作者提出按回答可行性在 RAG 与长上下文之间路由。实验模型、语料和成本条件均有限定，这不等于当前任意模型上长上下文必然更好。[原论文](https://arxiv.org/html/2407.16833v1)

《Don't Do RAG》提出 Cache-Augmented Generation：将可管理的知识集合预先编码为 KV cache，回答时复用。实验使用 Llama 3.1 8B 和 SQuAD、HotPotQA 的子集，资料规模约 21k–85k tokens；其结果支持小型固定知识集的一种可行方案，不能证明个人资料问答已解决。论文也报告随上下文扩大，优势收窄。缓存收益取决于预计算和复用，不能把每次重发全文直接等同于论文里的 CAG。[原论文](https://arxiv.org/html/2412.15605v2)

## 对 Jotway 的建议

以下是从上述路径推导的产品建议。先将小数据的完整上下文作为比较基线，再根据实际质量和等待时间决定是否增加检索与摘要。无需先建设复杂筛选流水线。

| 用户问题 | 建议收集方式 | 回答边界 |
|---|---|---|
| 我这周忙什么 | 先明确本地时区下本周起止，获取三源在此范围内的记录；补充与本周有关、但建于更早时间的计划和任务。范围内数据少时整体传入 | 区分已经安排、尚待完成和已有完成证据。日历时段不证明真实参与，也不代表实际耗时 |
| 我最近在做什么 | 用可见的默认范围，例如最近 14 天，覆盖三源后按项目和主题归纳；需要时关联更早的目标或背景 | 最近修改的笔记只能证明最近有修改，不能独自证明最近执行了文中活动。没有记录不等于没做 |
| 我是什么样的人 | 数据少时看整个已授权范围；数据多时先覆盖不同时间和主题的摘要，再补取支撑、反例和变化的原文 | 输出有证据的兴趣、行为模式或暂时倾向。区分本人表达与摘录、收藏；避免把一次计划写成人格定论 |
| 上次决定怎样优化快捷输入 | 围绕具体项目、决定和相关表述做定向检索，必要时读取完整笔记或相关事项 | 保留决定日期与后续变化；新记录是否推翻旧记录要依据内容判断 |

“相关”在宽泛问题中意味着能帮助构成完整图景，不一定是与问题字面相似。先用相似度删掉大量记录，可能正好删掉用于发现主题的材料。完整上下文允许回答模型在阅读后判断哪些材料有用，代价是更多输入和可能的干扰。

建议让问题整理模型输出问题类型、对象、时间范围和歧义，而非每次强制扩写一批关键词。完整上下文路径可以跳过查询扩写；明确的日期范围也可以直接解析。三源均参与收集，不需要为每个来源强行保留相同数量的记录。

## 全量输入仍需清楚的范围

全量指本次已授权资料范围内可用的文本，不代表绕过来源开关，也不代表只发送各来源的前几条。每条材料应附来源标识、标题、时间字段含义和状态；明确区分事件时间、完成时间、创建时间和修改时间。内容去重和清理 HTML 可以减少重复，但不应暗中删除会改变结论的原文。

实现这一建议需要先支持范围内的记录枚举和正文组装；把现有检索的 top-k 调大，仍不等于完整覆盖。

上下文预算需按所选模型计算，给系统说明、会话历史和输出留余量。超限时应报告覆盖范围并选择扩大预算、分批摘要或定向检索，不能静默截断后宣称已理解全部资料。缓存失效、来源更新与摘要引用应有对应机制，以免旧摘要遮住新的状态。

能装入上下文不代表模型必然完整利用所有内容。Google 的长上下文指南说明，多条关键信息的提取表现不能直接由单条信息检索的高准确率推断；更长输入通常也增加首字等待时间。因此，全量方案仍需核验遗漏和延迟。[官方指南](https://ai.google.dev/gemini-api/docs/long-context)

## 选择方案的最低验证

用同一组脱敏或合成资料比较完整上下文、定向检索和按时间范围收集三种方式。样例同时覆盖具体事实、每周安排、近期活动和跨时间的个人倾向；检查关键证据是否遗漏、安排是否误写成完成、推论是否带依据，以及回答耗时和输入量。若完整上下文已达到质量和延迟要求，额外的检索链路需要用明确收益证明必要性。
