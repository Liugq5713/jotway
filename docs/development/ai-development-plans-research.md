# AI 开发方案的可读性与维护方式

> Role: **Reference**
> 调研日期：2026-10-09

面向「写方案 → Multica 派发 → fork review → 合入开发分支」的流程，方案需要同时回答三个问题：为什么做、具体怎样改、如何判断完成。固定标题能降低阅读成本；可观察的验收场景、明确的依赖和持续更新机制，才能让同一份方案支撑编码与 review。

直接使用：[五段模板](#建议试用的五段模板)与[提示词](#可以直接交给-ai-的提示词)。阅读一份方案时，先看第 1 节背景与目标和第 4 节验收条件，再展开风险最大的模块。

## 三种官方实践

以下是官方文档和模板所定义的做法；最后一列是结合当前工作流的适用性判断，不代表工具效果排名。

| 实践 | 官方结构与机制 | 值得借用的部分 | 使用代价与边界 |
| --- | --- | --- | --- |
| GitHub Spec Kit | 将功能规格、技术计划、执行任务分开。规格模板包含用户故事、边界情况、验收场景与成功标准；计划模板记录技术约束和目录结构。 | 先描述用户得到什么，再解释实现；给任务标注对应故事、文件路径与依赖。 | 完整流程可能生成研究、数据模型和接口等多份材料；小改动只借用必要字段即可。[规格模板](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)、[计划模板](https://github.com/github/spec-kit/blob/main/templates/plan-template.md) |
| OpenSpec | 当前规格与单次变更分开；变更包含 proposal、差量 specs、design 和 tasks。差量标明新增、修改、移除，完成后同步当前规格并归档变更。 | 针对已有系统写清「原来怎样 → 改成怎样」，避免重复整份产品文档。 | 多文件之间仍需保持一致；归档是文档生命周期操作，不等于验证通过或代码合并。[入门文档](https://github.com/Fission-AI/OpenSpec/blob/main/docs/getting-started.md) |
| Kiro Specs | 以 requirements、design、tasks 三类文件组织内容；Requirements-First 使用具体场景和验收标准，再产生组件、接口与执行任务。 | 明确区分行为约定与技术设计，并让每个任务有清楚的结果和前置依赖。 | 多文件不会自动消除维护成本；需求变更后仍需同步设计和任务。可借用格式，不需要更换现有派发工具。[Requirements-First](https://kiro.dev/docs/specs/feature-specs/requirements-first/)、[维护建议](https://kiro.dev/docs/specs/best-practices/) |

## 对当前方案格式有用的细节

1. **模块拆解之外，还要保留完整用户场景。** Spec Kit 的任务模板按用户故事组织，要求各故事能独立验证；公共基础任务单独列出，任务标注并行条件和具体路径。因此，「按模块讲怎么改」适合设计部分，「按用户场景判断完成」适合验收部分。[任务模板](https://github.com/github/spec-kit/blob/main/templates/tasks-template.md)

2. **把方案 review 放到编码前。** OpenSpec 建议先检查意图和范围，再检查需求场景，最后检查任务与需求是否对应；实现后再核对完整性、正确性与设计一致性。前后两次阅读承担不同目的，不能只靠最后看 diff。[Reviewing a Change](https://github.com/Fission-AI/OpenSpec/blob/main/docs/reviewing-changes.md)

3. **每条验收写一个可观察的行为。** OpenSpec 将行为要求与技术实现分开，要求场景真正覆盖对应要求，并包含重要边界与失败情形。「失败时保留草稿并允许重试」比「增强健壮性」更容易检查。[Writing Good Specs](https://github.com/Fission-AI/OpenSpec/blob/main/docs/writing-specs.md)

4. **实现发现变化时，同步修改原方案。** OpenSpec 允许持续调整方案与任务；代码和规格有分歧时，需要先判断哪一方正确，再使两者一致。同一目标的修正留在当前变更，目标根本变化则另起变更。[Editing and Iterating](https://github.com/Fission-AI/OpenSpec/blob/main/docs/editing-changes.md)

5. **复用必须有具体对象和理由。** Spec Kit 计划模板要求说明增加复杂度的必要性，以及拒绝更简单方案的原因。结合本仓库「优先使用已有函数和类型，只为已证明的复用引入抽象」的规则，共用部分应写清复用谁、由谁维护、哪些调用方会受影响，而不是只写「抽一个公共层」。[计划模板](https://github.com/github/spec-kit/blob/main/templates/plan-template.md)、[仓库规则](../../AGENTS.md)

## 在本仓库应用时的边界

这些工具提供了可借用的结构，不构成必须采用其 CLI、目录或审批机制的理由。对当前工作流，可以先使用一份有固定结构的 Markdown 方案；出现独立维护需求后，再拆出技术设计或任务文件。模板增加的字段应能帮助阅读、派发或验收，否则只会增加需要同步的内容。

格式校验与任务勾选只能提供结构或进度信息。OpenSpec 的 `validate` 在入门文档中用于校验规格格式，`verify` 则读取方案与代码报告差异；这些结果仍不能替代构建、运行检查或真实窗口行为的验收。交接时应分别说明执行了什么验证、观察到什么结果。[入门文档](https://github.com/Fission-AI/OpenSpec/blob/main/docs/getting-started.md)、[Reviewing a Change](https://github.com/Fission-AI/OpenSpec/blob/main/docs/reviewing-changes.md)

Jotway 已区分 Current、Work、Reference 和 Decision：活动方案属于 Work；完成后将实际行为并入 Current，删除 Work，由 Git 保留历史。因此可以借用 OpenSpec 的「变更回灌当前规格」思想，但本仓库应继续遵守自己的文档生命周期，不直接照搬 `changes/archive/`。[仓库文档约定](../../AGENTS.md)

## 让人愿意读的方案

Basecamp 的 Shape Up pitch 固定说明问题、投入上限、方案、容易陷入的细节和明确不做的范围，并建议用一个具体场景解释现状为何不够好。这里的投入上限是愿意花多少时间，不是预测开发耗时。[Write the Pitch](https://basecamp.com/shapeup/1.5-chapter-06)

Rust RFC 模板先给摘要与动机，再区分面向使用者、通过示例解释的部分，以及实现所需的技术细节；另列缺点、替代方案和未决问题。这种阅读层次适合借用，完整 RFC 的篇幅和仪式则可以按改动规模裁剪。[Rust RFC 模板](https://github.com/rust-lang/rfcs/blob/main/0000-template.md)

对当前流程，建议将首屏作为约一分钟能读完的决策摘要：具体问题、目标行为、涉及模块、最大风险和待决定事项。正文再按模块展开。这个阅读目标是试用约束，不是社区统一标准；复杂方案需要更长说明时，把细节放在对应模块下，并保留摘要到详情的入口。

## 建议试用的五段模板

以下是一份 Work 方案的格式建议。小改动保留五个标题，每节写几句话；复杂改动在对应节内展开。当前行为附代码或 Current 文档依据，建议新增的类型明确标注「拟新增」，没有仓库证据的内容标注「待核实」。

表格行只是示例，按实际需要增删。小改动每节可只写一句，执行与交接可用一条验证说明，不强制拆成多个任务。

```markdown
# 改动名称

> Role: Work
> 状态：草案 / 可派发 / 实现中 / 待验收
> 依据：相关 Current 文档；代码基线 branch@commit

## 1. 背景与目标

用一个实际场景说明：谁在什么情况下遇到什么问题。
当前行为 → 目标行为：用操作或输入输出举例。
范围：本次覆盖什么、明确不做什么。
摘要：涉及模块、最大风险、需要用户决定的事项；没有则写无。

## 2. 模块改动

### 模块名

- 职责与入口：模块做什么；已核实的文件、类型或函数。
- 行为变化：原来怎样 → 改完怎样。
- 具体改动：新增、修改或删除什么；为什么选择这个落点。
- 改动影响：影响哪些调用方、状态、数据或接口；相关风险。
- 对应验收：引用 A1 等编号；共享规则引用第 3 节。

其他模块采用同一格式，只写各自负责的变化。

## 3. 共用部分与取舍

已有能力：复用哪个具体入口，当前有哪些调用方。
共享约定：跨模块的数据、接口或业务规则在这里定义一次。
新增抽象：由谁拥有、哪些真实调用方需要、为什么现有实现不够。
依赖顺序：哪些约定需要先确定，哪些改动可独立进行。
关键取舍：选什么、为什么；无新增共用部分时明确写明。

## 4. 验收条件

| 编号 | 前置条件与操作 | 可观察的结果 | 验证方式 |
| --- | --- | --- | --- |
| A1 | 主要成功场景 | 具体输出或用户行为 | 既有测试 / 命令 / 手工检查 |
| A2 | 相关失败或边界场景 | 明确的恢复或提示行为 | 对应检查方式 |
| A3 | 受影响的原有场景 | 必须保持的具体行为 | 对应检查方式 |

未决问题：说明影响；会改变目标、范围或验收的事项在派发前解决。

## 5. 执行与交接

| 任务 | 完成结果 | 依赖 | 覆盖验收 |
| --- | --- | --- | --- |
| T1 | 一项可检查的结果 | 无或具体前置任务 | A1 |
| T2 | 一项可检查的结果 | T1 或可独立执行 | A2、A3 |

验证安排：准确的命令或操作；哪些需要人工确认。
交付回执：方案版本、代码版本、偏离及原因、逐项验证结果。
文档收尾：实际行为合入哪些 Current 文档，再删除本 Work 及索引。
```

「模块改动」说明设计归属，「执行任务」按可以检查的结果拆分；一个用户行为可能跨多个模块，不必把每个模块自动派给不同 agent。涉及共用接口时先明确其约定与负责人，再安排有依赖的工作。

复用章节应允许得出「沿用现有实现，不新增抽象」。看起来相似的代码未必承载同一条业务规则；应说明真实调用方为什么需要一起变化。Google 的 review 指南也要求检查复杂度，警惕为尚不存在的需求提前泛化。[Google code review 指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

## 接入现有工作流

以下为当前工作流的适配建议。

1. **写方案时先核实现状。** 在终端读取相关代码和 Current 文档后填写模块入口。在 ChatGPT 中起草但没有仓库上下文时，保留待核实项，由能读仓库的 agent 补齐后再派发。你先看第 1 节和第 4 节，再展开风险最大的模块。
2. **派发时固定可取回的方案版本。** 交接中带上方案路径与 commit；未提交方案则提供完整快照及内容摘要值，同时标明代码基线。确保执行 agent 能读取这份内容，不能只给另一个 worktree 中不存在的本地路径。
3. **编码时更新同一份方案。** 实现位置变化时修订对应模块，并在交接中说明原因；目标、范围或验收变化时先让用户决定。保留派发快照供比较，避免通过事后降低验收条件把缺失实现改成完成。
4. **fork review 时同时看方案和代码。** 输入包含派发快照、最新方案、基线 commit 与待审 commit。逐项输出「验收编号 → 实现依据 → 已做验证 → 通过 / 不通过 / 未验证」，另外检查方案外的回归和复杂度。reviewer 自行核实证据，执行 agent 的完成回执只是输入。
5. **合并时核对最终候选。** quick action 合并的内容应与 review 对象一致；冲突解决或目标分支变化后，检查最终组合差异并验证受影响部分。构建通过、代码 review、安装状态和人工体验验收分别记录。文档收尾沿用仓库现有 Current / Work 规则。

例如一条验收写「保存失败时保留原文，用户可以重试」，review 回执就应指向实际失败恢复分支及对应检查结果。只运行构建时，该条行为仍是未验证；截图只能说明展示状态，不能证明重试没有重复执行。此例说明验收与证据的对应方式，不代表当前项目存在待修复问题。

## 可以直接交给 AI 的提示词

```text
请先阅读仓库规则、相关当前文档和代码，再为这次改动写开发方案。
使用固定五节：背景与目标、模块改动、共用部分与取舍、验收条件、执行与交接。

1. 首屏用具体场景说明当前问题和目标行为，列出范围、主要风险与待决定事项。
2. 按模块写已核实入口、原来怎样、改成怎样和影响谁；拟新增与待核实内容明确标注。
3. 共用部分写具体已有能力、真实调用方和归属；新增抽象说明现有实现为何不够。
4. 给验收编号，写清前置条件、操作、可观察结果和验证方式；任务引用验收编号。
5. 输出前检查目标是否都有验收、任务是否都有完成条件、共享规则是否只定义一次。

先输出方案供我阅读；本次工作只到方案，不派发或编码。
```
