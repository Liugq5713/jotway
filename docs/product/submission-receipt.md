# 提交完成回执：需求与实现方案

> Role: **Work**
> Status: 待实现；本文定义目标行为，不代表当前已交付。
> Priority: **P1**

## 目标与场景

用户提交一句话后，继续在原应用工作，也能轻轻确认这次操作到了哪里、是否完成。只有想查看结果时才打开目标应用；连续录入不会产生一串互相覆盖的提示。

核心验收：成功存入后，用户无需重新打开快速记录面板或 Notes 来判断是否成功，也不会因反馈缺失而再次提交同一内容。

## 当前行为与问题

- [LauncherSession.submit](../../Sources/Features/Launcher/LauncherSession.swift) 先清空草稿，创建执行任务并隐藏面板，然后等待执行结果。退场动画表示提交受理，不代表目标已经创建内容。
- 成功结果写入 `applicationNotice`，到下一次 `prepare(quote:)` 才进入 `state.message`。连续成功会覆盖这个单值提示，无法逐次确认结果。
- 失败通过 `restoreAfterFailure` 恢复原草稿；已有新输入或正在组词时，保留为 `FailedSubmission`，避免覆盖新草稿。
- [ActionOutcome](../../Sources/Actions/LauncherAction.swift) 已有结构化 `effect` 和本地化文案。存入类 action 取得创建标识后才返回成功；当前结果没有携带供回执展示的实际目标位置和打开入口。

当前执行顺序以 [Architecture](../development/architecture.md) 和代码为准；[Product overview](overview.md) 的“成功后清空关闭”概述尚未表达先退场、后完成的区别，实现交付时一并澄清。

## 范围与完成语义

P1 覆盖 Notes、Reminders、Calendar 的存入回执，并让 Chrome、ChatGPT 使用同一反馈通道表达各自真实结果。纯应用启动已有目标应用出现，本期不另加成功回执；Notes 配置入口不是执行，不进入回执统计。

| Action | 可据以反馈的事实 | 单次回执示例 | 按需入口 |
|---|---|---|---|
| Notes | 目标适配器确认创建 note 标识 | `Saved to Notes · Work` | `Open Notes` |
| Reminders | EventKit 保存成功且返回 reminder 标识 | `Created in Reminders · Personal` | `Open Reminders` |
| Calendar | EventKit 保存成功且返回 event 标识 | `Created in Calendar · Work` | `Open Calendar` |
| Chrome | macOS 受理打开搜索 URL 的请求 | `Search opened in Chrome` | `Open Chrome` |
| ChatGPT | macOS 受理打开带草稿的链接请求 | `Opened ChatGPT · Review and send there` | `Open ChatGPT` |

表中为英文产品文案示意，沿用项目的英文 UI 和语义本地化键。目标位置使用本次实际执行的文件夹、列表或日历名称；必要时附账户名消歧。正文、首行标题和全文预览不进入回执。

“已创建”只承诺目标适配器确认的写入，不承诺云端同步或其他设备可见。Chrome 不承诺网页加载完成。ChatGPT 当前 `.prefilled` 结果不足以证明实际预填，更不代表发送成功；本期文案必须保留“到目标应用检查并发送”的边界，不解析字符串来推断成功。

## 交互要求

### 提交与等待

1. Enter 确认、草稿清空与面板退场沿用现有流程；不等待写入完成才让用户继续工作。
2. 只有本次提交已被执行管线受理，才能进入待完成状态。编辑器拒绝清空、空草稿、配置流程、重复按键被拦截均不产生回执。
3. 提交后 **800 ms** 仍未结束，显示中性等待提示，例如 `Saving to Notes…`；不显示成功勾选。更快完成时直接显示结果，避免等待态闪烁。
4. 执行没有返回时不因展示计时器而改判失败或成功，不自动重试，也不重新发送正文。慢请求继续显示等待状态；本需求不新增执行超时策略。

### 完成回执

- 使用独立、非激活的轻量回执窗口，不重新打开快速记录面板。收到结果后立即更新，正常 UI 调度下 **300 ms 内**可见；不等待下一次唤起，也不等待退场动画结束。
- 单条回执包含目标应用图标、结果、目标位置（适用时）、`Open …` 按钮和关闭按钮。成功有勾选与文字，不能只靠颜色区分。
- 默认在提交面板所在屏幕的右下角，距可见区域边缘 **16 pt**，宽 **320 pt**；窄可见区域内缩到可容纳宽度。位置由提交时的屏幕快照决定，显示后不随鼠标移动；屏幕断开时回退至当前可用屏幕并约束到可见区域。
- 自动出现、内容更新、淡出和关闭都不得激活 Jotway、取得 key/main window、改变第一响应者、切换 Space，或干预中文组词。Chrome、ChatGPT 仍由原 action 的窗口策略保留目标应用在前台。
- 一批执行全部结束后停留 **4 秒**，随后淡出。新结果在原位置更新并重置这 4 秒；鼠标悬停或辅助功能正在操作回执时暂停淡出，离开后重新给足 4 秒。仍有执行中项时不自动隐藏。
- 默认无声音、无 Dock 跳动、无系统通知授权。浅色、深色、增强对比度遵循现有中性表面；减少动态效果时直接显隐。长位置名可截断，但保留完整辅助功能标签。
- 回执出现时不自动移动辅助功能焦点；目标、状态和按钮必须可被辅助功能访问。回执不注册全局 Enter/Escape 监听，用户在原应用的按键继续交给原应用。
- 用户再次打开快速记录面板时，回执不覆盖编辑区、候选列表或输入法候选窗；必要时调整回执位置。已有新草稿、选区与撤销状态保持原样，回执不占用动作行，也不再把已展示成功写回 `applicationNotice`。

### 按需打开目标应用

- 仅在用户点击 `Open …` 或通过辅助功能主动触发该按钮后，打开并激活对应应用；完成回执本身不会打开目标应用。
- P1 入口保证到达目标应用，不承诺定位刚创建的具体内容。按钮必须写 `Open Notes` 等应用名，不写 `View this note`。
- 使用 action 提供的稳定应用标识或经过验证的应用目标；窗口层不按 action ID 硬编码应用映射，不用正文拼接 shell 或推断深链接。
- 打开操作与原执行分离：禁止再次调用 `PreparedAction.execute`。Chrome 不重复搜索，ChatGPT 不重复创建带草稿的会话，存入类 action 不重复创建内容。
- 用户主动打开时允许切换前台；若有正在编辑的新草稿，沿用现有保留规则。打开失败只显示 `Saved, but couldn’t open Notes` 等对应结果的安全提示，保留原成功事实；不得恢复已成功提交的草稿或把原执行改记为失败。

## 连续录入与并发

回执维护一个内存中的当前反馈批次，不提供可浏览的提交历史。

1. 第一笔被受理的提交创建批次。批次仍有执行中项或回执仍在展示时，后续提交加入同一批次。最后结果展示满 4 秒并淡出后，下一笔提交建立新批次。
2. 全局最多一个回执窗口。展示按目标应用汇总，同一应用只有一行，例如 `Notes · 3 saved · 1 saving`；内部按 `actionID + destinationID + effect` 分组，不能用位置名称作身份。同一位置显示其名称；多个位置显示 `2 folders` 等数量，不把所有结果标成最后一次的目标，同名但不同账户的位置仍分别计数。不同应用各有 `Open …` 入口。
3. 最多直接展示三组，更多组通过 `More results (N)` 在用户主动展开后查看同一批次的其余应用汇总；不展示逐条正文或历史列表。展开视图同样不自动夺取键盘焦点。
4. 每次提交拥有独立的运行时标识；按标识只结算一次，允许乱序完成。成功数仅增加已确认成功的项，待完成、失败和未知结果分开计数。不得把整批写为“全部成功”，直到所有项都已确认成功。
5. 等待提示的 800 ms 按各提交起点计算；若回执已经可见，新加入的执行直接更新待完成数。批次跨屏时沿用第一笔提交的屏幕，避免提示来回跳动。
6. 手动关闭只关闭展示，不取消执行，并抑制已有提交尚未触发的 800 ms 等待提示。旧结果不单独触发展示；新提交或在途项的新结果可再次展示，计数仍保留整批事实。例如 A 已成功、B 在途时关闭，B 成功后显示 `2 saved`。没有在途项时关闭即结束批次；在途项仍按原标识结算，不能丢失或重复计数。
7. 失败、未知结果不被后续成功覆盖。含异常的批次展示各类数量，例如 `Notes · 2 saved · 1 not confirmed`；原有错误提示和草稿恢复入口继续保留，不随成功回执淡出而清除。

## 失败与不确定结果

- 确认失败继续走现有 `restoreAfterFailure`：没有新草稿时恢复原文；已有新输入或中文组词时不覆盖，保留失败提交。完成回执只补充即时反馈，不重做草稿恢复机制。
- `ActionFailure` 标记效果未知，或 `ActionOutcome.effect == .unknown` 时，显示 `Couldn’t confirm save · Check Notes before retrying` 等中性异常提示，不显示成功勾选，也不把“不抛错”当作已创建。
- 扩展 action 返回 `.accepted` 时仅显示“请求已受理，尚未确认完成”，与已完成数量分开；它是本次调用的终态，不永久计入仍在执行数。返回 `.failed` 或 `.unknown` 同样必须按结构化结果进入失败或未知分支，不能因为没有抛错而进入成功分支。
- 未知结果保留可人工恢复的原稿和目标应用入口，用户核对后才能决定是否重试。无论错误还是未知结果，都没有自动重试；用户重新确认才产生新的执行尝试。
- 单次成功与失败乱序到达时，成功回执不能清除 `FailedSubmission`、替换当前错误提示或触发恢复。展示层关闭、计时器触发、打开应用失败都不参与原执行结算。
- 当前仅有一个 `FailedSubmission` 槽位；本期不扩展为失败队列，也不宣称解决多笔并发失败的原稿保留问题。若实现需要支持多笔失败逐条恢复，应另开需求，不用回执状态暗中承载正文历史。

## 实现落点

| 位置 | 计划修改 |
|---|---|
| [LauncherAction.swift](../../Sources/Actions/LauncherAction.swift) | 在 descriptor 提供可选的稳定应用身份和打开目标；为 `ActionOutcome` 增加可选结构化回执信息：实际目标应用、位置标识与名称。沿用现有 `effect` 和本地化边界，兼容未提供回执元数据的 action；禁止从成功字符串解析目标。 |
| [ActionModule.swift](../../Sources/Actions/ActionModule.swift) 的 `ActionExecutionSnapshot` | 从模块取得并冻结本次提交的回执上下文，包含应用身份、打开入口和已知位置；与执行 action 使用同一配置快照。等待态、准备失败和执行抛错均可取得该上下文，不依赖成功后才有的 `ActionOutcome`。 |
| Notes / Reminders / Calendar action | 在本次准备与执行闭包中冻结目标快照，确认创建后返回对应回执信息；不在完成回调重新读取可能已改变的设置。创建标识继续作为确认依据，P1 不为精确跳转增加读取或权限请求。 |
| Chrome / ChatGPT action | 提供实际目标应用与准确的结果文案；回执的打开入口只打开应用，不复用搜索 URL 或带正文的链接。 |
| [LauncherSession.swift](../../Sources/Features/Launcher/LauncherSession.swift) | 在提交受理和最终结算位置发出结构化事件，复用一次提交已有的 `requestID`，而非依赖可关闭的本地操作记录。成功从 `applicationNotice` 分离；失败保持原恢复分支，未知结果显式处理。 |
| 新增 `ExecutionReceiptState`（建议置于 `Sources/Features/Launcher/`） | 只维护当前批次的标识、分组、计数、目标元数据和展示期限；不存正文、不访问窗口、不重新执行 action。UI 状态在 `@MainActor` 更新。 |
| [PanelController.swift](../../Sources/Window/PanelController.swift) 与新增 `ExecutionReceiptPanel` | 解释回执展示、位置、关闭、计时和按需打开效果，托管独立非激活窗口。复用现有窗口选屏/打开应用的适配边界；不要调用会执行 `makeKey` 的 `RecordPanel.showPanel()` 显示回执。 |
| [Localizable.strings](../../Sources/Resources/en.lproj/Localizable.strings) | 增加等待、完成、部分完成、未知、打开失败、计数与辅助功能文案；处理单复数及长目标名称。 |

回执事件至少携带运行时提交标识、action 身份、冻结的目标快照和结构化状态。目标位置在准备完成前不可确定时，等待态及准备失败仅显示应用名；若准备阶段进一步解析位置，需把该快照传入执行和异常回调，最终结果使用实际执行目标。没有打开能力的扩展 action 隐藏按钮，不构造猜测入口。

执行任务、展示计时器与窗口生命周期分开：清空新草稿、配置变更、关闭回执均不能取消已受理执行；旧批次的淡出回调不得关闭新批次。使用批次标识或代次检查取消过期回调。进程退出清理展示任务和窗口，不持久化回执，也不在重启后重放。

原有 `OperationRecorder` 继续按执行尝试记录真实结果。合并计数只影响展示，不能合并、补造或改写执行事实；关闭本地操作记录后回执仍可工作。无需数据库迁移，不将正文、创建标识或带正文的 URL 加入运行时日志。

## 验收与验证

| 场景 | 必须观察到的结果 |
|---|---|
| Notes 正常存入，用户不再打开面板 | 确认创建后 300 ms 内出现 `Saved to Notes` 与实际文件夹，停留约 4 秒；目标内仅新增一条。用户能直接说出结果和目标，无需再查 Notes。 |
| 保存需要 3 秒 | 800 ms 后出现 `Saving…`，确认创建前没有成功态；完成后转成功，新输入不受阻。 |
| 请求一直没有返回 | 仍为等待，不伪报成功/失败、不超时重发；手动关闭不取消原执行。 |
| 4 秒内连续提交 3 条 Notes | 一个窗口一行聚合为 `3 saved`，过程中正确显示待完成数；目标实际新增 3 条，无重复写入。 |
| 同一批次变更 Notes 文件夹，再提交 Calendar | 各提交保留实际目标快照；Notes 显示多个位置，Calendar 单独计数并提供正确入口，不读取最后设置覆盖旧目标。 |
| A 慢、B 快，结果倒序返回；重复结算回调 | A、B 各计数一次；B 的结果先可见，A 完成后更新同一批次。旧计时器不关闭新结果。 |
| 一笔成功、一笔失败或未知 | 分别计数，永不展示“全部成功”；异常原稿仍按现有机制保留，新草稿不被成功回执覆盖。 |
| 外部应用持续输入 / 面板内中文组词 | 回执显隐、聚合更新均不改变活动应用、key window、第一响应者、选区或 marked text，原按键不中断。 |
| 点击 `Open Notes`，以及打开应用失败 | 只有主动点击才切换应用，不新增 note；打开失败保留“已存入”事实，新草稿和失败恢复状态不变。 |
| Chrome / ChatGPT 完成 | 保持目标应用在前台；不宣称网页加载或消息发送完成；再次点打开入口不重发原 URL。 |
| 关闭回执、再次唤起面板、关闭本地操作记录 | 不取消执行、不重放旧成功提示、不生成新执行尝试；记录关闭不影响回执。 |
| 三个以上应用、长目标名、多屏断开、浅深色与辅助功能 | 汇总和按需入口可访问，无越界、正文泄漏、编辑器遮挡或自动焦点转移；悬停暂停计时，减少动态效果可用。 |

实施顺序：先补结果元数据与提交事件，再接批次状态和窗口，最后完成聚合、异常与打开失败分支。每步保留现有准备缓存、重复提交防护和新草稿保护。

代码实现后运行 `swift build`，以及相关既有 `LauncherActionTests`、`JevPanelTests`、`MainPathTests`。需要补充验证时，使用隔离依赖、离屏窗口和可控完成顺序的最小真实用例；按 [AGENTS.md](../../AGENTS.md)，未经用户要求不新增测试文件或自动启动、驱动用户的 Jotway.app。真实焦点、输入法、全屏 Space 与辅助功能交互列为手工验收；不能用构建通过代替。

体验验收由用户按“提交后继续做原来的事”完成一次单条存入与一次连续录入，不预先引导打开 Notes；两次都能仅凭回执判断完成与目标，且不因不确定而重复提交。判断失败时继续调整可见时长、位置或文案，不以“有提示窗口”代替验收。

## 非目标与文档收尾
